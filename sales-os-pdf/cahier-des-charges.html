Section 1
Presentation du projet
1.1 Nom
SALES OS
1.2 Nature du projet
SALES OS est une application web de gestion et de pilotage commercial destinee a centraliser l'ensemble du cycle de vente d'une entreprise.
La plateforme permettra notamment de gerer :
  • les maisons / points de vente
  • les utilisateurs
  • les agents de terrain
  • les portefeuilles clients
  • les prospects et clients
  • les produits
  • les commandes
  • les ventes
  • les paiements
  • les stocks
  • les commissions
  • les objectifs commerciaux
  • les performances
La solution sera concue des le depart avec une architecture permettant son evolution vers un SaaS multi-entreprises, sans que cette evolution soit necessairement activee commercialement dans le MVP.
Section 2
Contexte et problematique
L'activite commerciale de l'entreprise implique plusieurs maisons, agents, clients et operations de vente. Lorsque ces informations sont suivi separement, plusieurs difficultes peuvent apparaitre :
  • manque de visibilite globale
  • difficulte a connaitre les performances de chaque maison
  • difficulte a mesurer la performance des agents
  • perte ou duplication d'informations clients
  • difficulte a suivre les commandes non finalisees
  • erreurs dans le calcul des commissions
  • manque de visibilite sur les paiements
  • difficulte a suivre les stocks
  • absence d'un historique centralise des operations
  • difficulte a mesurer l'atteinte des objectifs mensuels
SALES OS doit resoudre ces problemes en mettant en place un systeme commercial centralise, securise et structure.
Section 3
Vision du produit
SALES OS doit devenir le centre de pilotage commercial de l'entreprise. Le proprietaire doit pouvoir acceder a une vision globale de l'activite :

Combien avons-nous vendu ?

Quelle maison vend le plus ?

Quel agent apporte le plus de clients ?

Quels clients sont reguliers ?

Quelles commandes sont encore en attente ?

Combien de commissions ont ete generees ?

Ou en sommes-nous par rapport a notre objectif mensuel ?

Quelle est la contribution de chaque maison ?

L'objectif est donc de transformer les donnees commerciales en informations directement exploitables pour la prise de decision.
Section 4
Objectif general
Mettre en place une plateforme permettant de :

Centraliser, securiser, suivre, mesurer et piloter l'ensemble du processus commercial de l'entreprise, de la prospection jusqu'a l'analyse des performances.

Section 7
Utilisateurs et roles
7.1 Gestionnaire principal
Le gestionnaire principal represente la direction de l'entreprise.
Il dispose d'une vision globale et peut notamment :
  • gerer les maisons
  • gerer les utilisateurs
  • gerer les agents
  • consulter les clients
  • consulter les ventes
  • gerer les produits
  • suivre les stocks
  • definir les objectifs
  • gerer les regles de commission
  • consulter les rapports
  • controler les performances
7.2 Responsable de maison
Il gere l'activite de sa maison.
Il peut, selon ses permissions :
  • consulter ses agents
  • suivre les clients
  • suivre les commandes
  • suivre les ventes
  • consulter le stock
  • suivre les performances de la maison
Il ne doit pas acceder aux donnees des autres maisons si ses permissions ne l'y autorisent pas.
7.3 Agent de terrain
L'agent est charge notamment de developper et gerer son portefeuille commercial.
Il peut :
  • enregistrer des prospects
  • creer des clients
  • gerer son portefeuille
  • creer des commandes
  • suivre ses ventes
  • consulter ses commissions
  • suivre ses performances
7.4 Vendeur
Le vendeur peut effectuer les operations commerciales qui lui sont attribuees.
  • consulter les produits
  • creer ou traiter une commande
  • enregistrer une vente
  • consulter les informations necessaires a la vente
7.5 Caissier / gestionnaire financier
Il peut :
  • enregistrer les paiements
  • consulter les ventes concernees
  • suivre les soldes
  • gerer les operations financieres autorisees
7.6 Gestionnaire de stock
Il peut :
  • gerer les produits
  • enregistrer les entrees
  • enregistrer les sorties
  • effectuer les ajustements autorises
  • suivre les niveaux de stock
Section 8
Gestion des maisons
Une maison represente un point de vente, une agence ou une unite commerciale.
Exemple :
ENTREPRISE │ ├── Maison Kinshasa ├── Maison Lubumbashi ├── Maison Goma └── Maison Matadi
Chaque maison peut disposer de :
  • responsable
  • utilisateurs
  • agents
  • clients
  • commandes
  • ventes
  • stock
  • statistiques
La direction dispose d'une vue consolidee de toutes les maisons.
Section 9
Gestion des agents
Chaque agent dispose d'un profil commercial. Le systeme conserve notamment :
  • identite
  • maison
  • statut
  • portefeuille
  • clients apportes
  • ventes
  • performances
  • commissions
La direction pourra comparer les performances des agents.
Section 10
Portefeuille client de l'agent
Tout client apporte par un agent doit etre enregistre dans son portefeuille.
AGENT ↓ PORTEFEUILLE ↓ CLIENT ↓ COMMANDES ↓ VENTES
Le systeme conserve l'agent ayant initialement enregistre le client. Cela permet de determiner clairement l'origine commerciale d'un client.
Section 11
Attribution et transfert des clients
Un client possede un agent referent.
Lorsqu'un agent enregistre un nouveau client, le systeme verifie les eventuels doublons.
Si le client existe deja :
  • une alerte est affichee
  • le systeme indique qu'un autre agent est deja associe
  • le nouveau rattachement ne peut pas etre effectue automatiquement
Le transfert d'un client vers un autre agent necessite l'autorisation d'un responsable habilite.
L'historique conserve :
  • ancien agent
  • nouvel agent
  • date
  • utilisateur ayant effectue le transfert
  • motif, si renseigne
Section 12
Gestion des clients
Le systeme distingue notamment :
Prospect → Nouveau client → Client actif → Client regulier → Client inactif
Les criteres permettant de qualifier un client de regulier ou inactif pourront etre configures.
Pour chaque client :
  • nom
  • telephone
  • email
  • adresse
  • agent referent
  • maison
  • historique
  • commandes
  • ventes
  • montant des achats
  • frequence d'achat
  • derniere activite
La recherche devra permettre de retrouver rapidement un client.
Section 13
Commandes
Une commande represente une intention d'achat. Elle ne constitue pas automatiquement une vente.
Les etats sont :
Brouillon ↓ En attente ↓ Formalisee ↓ Confirmee ↓ Transformee en vente
Une commande peut egalement etre : Annulee
Le gestionnaire pourra consulter les commandes non encore transformees en ventes. Cela permettra notamment de suivre les opportunites commerciales en attente.
Section 14
Ventes
Une vente represente une transaction effectivement confirmee.
Une vente pourra etre creee :

soit directement,

soit a partir d'une commande existante.

Chaque vente doit conserver :
  • entreprise
  • maison
  • client
  • agent apporteur
  • vendeur
  • produits
  • quantites
  • prix
  • montant
  • date
  • mode de paiement
  • etat du paiement
Section 15
Agent apporteur et vendeur
Afin d'eviter toute ambiguite, le systeme distinguera :
Agent apporteur
Agent ayant cree ou acquis le client.
Vendeur
Personne ayant effectivement realise la vente.
Exemple :
Patrick ↓ apporte Jean ↓ Jean appartient au portefeuille de Patrick ↓ Jean achete a la Maison B ↓ Marie realise la vente
Le systeme conserve donc : Agent apporteur = Patrick / Vendeur = Marie
Les regles de commission determineront ensuite qui est remunere.
Section 16
Produits et catalogue
Chaque entreprise possede son propre catalogue. Un produit peut comporter :
  • reference
  • nom
  • categorie
  • description
  • unite
  • prix
  • statut actif/inactif
  • image
  • suivi de stock
Les produits sont isoles par entreprise.
Section 17
Gestion des stocks
Le stock est suivi par maison. Le systeme enregistre :
Entrees
  • reception
  • retour
  • approvisionnement
Sorties
  • vente
  • transfert
  • sortie autorisee
Ajustements
  • inventaire
  • casse
  • perte
  • correction autorisee
Le stock disponible est recalcule apres chaque operation.
Section 18
Stock insuffisant
Le comportement en cas de stock insuffisant sera configurable.
Mode strict

La vente est bloquee si le stock disponible est insuffisant.

Mode souple

La vente peut etre enregistree avec une alerte.

Cette configuration appartient au gestionnaire principal.
Section 19
Paiements
Une vente peut etre payee :
  • integralement
  • partiellement
  • ulterieurement
Une vente peut donc avoir plusieurs paiements.
Exemple :
VENTE : 1 000 $ Paiement 1 : 300 $ Paiement 2 : 400 $ ---------------- Solde : 300 $
Etats financiers :
Impaye → Partiellement paye → Paye → Rembourse
La vente et son paiement doivent rester deux notions distinctes.
Section 20
Commissions
SALES OS integrera un moteur de commissions.
Dans le MVP, une regle simple pourra etre utilisee :

Pourcentage fixe sur une vente eligible.

Exemple : Vente : 500 $ — Commission : 10 % — Commission = 50 $
Le systeme conservera le lien :
Vente ↓ Agent beneficiaire ↓ Regle appliquee ↓ Commission
Section 21
Evolution du moteur de commissions
Dans les versions futures, les regles pourront prendre en compte :
  • pourcentage
  • montant fixe
  • produit
  • categorie
  • vendeur
  • agent apporteur
  • paliers
  • bonus
  • objectifs
Une entreprise pourra donc definir ses propres regles.
Section 22
Cycle de vie de la commission
EN ATTENTE ↓ VALIDEE ↓ PAYABLE ↓ PAYEE
En attente

Commission calculee mais pas encore validee.

Validee

Commission controlee par un responsable habilite.

Payable

Commission prete a etre versee.

Payee

Commission effectivement versee.

Une annulation ou un remboursement doit pouvoir entrainer une revision de la commission selon les regles de l'entreprise.
Section 23
Objectifs commerciaux
Le gestionnaire principal pourra definir un objectif mensuel.
Exemple : Target : 3 000 pieces
Le dashboard affichera :
OBJECTIF : 3 000 REALISE : 2 100 RESTANT : 900 PROGRESSION : 70 %
L'objectif pourra etre exprime selon les besoins :
  • quantite
  • chiffre d'affaires
  • nombre de ventes
Section 24
Objectifs par maison
Le gestionnaire pourra definir une contribution cible pour chaque maison.
Exemple :
Target global : 3 000 pieces Kinshasa 1 200 Lubumbashi 800 Goma 600 Matadi 400
Le systeme permettra de comparer : Objectif prevu vs Realise.

Section 29
Authentification
Chaque utilisateur dispose d'un compte personnel. Le systeme utilise :
Identifiant ↓ Mot de passe ↓ OTP ↓ Autorisation
Le mot de passe possede une duree de validite configurable, par exemple 30 a 60 jours.
Le gestionnaire principal peut :
  • activer un utilisateur
  • desactiver un utilisateur
  • reinitialiser son acces
  • revoquer ses sessions
Le mecanisme OTP devra etre concu pour etre securise et operationnel sans dependre d'une intervention manuelle du gestionnaire a chaque connexion.
Section 30
Permissions
Les permissions seront definies par :
Role + entreprise + maison + perimetre personnel.
Les actions pourront etre :
  • consulter
  • creer
  • modifier
  • valider
  • annuler
  • supprimer
Certaines operations sensibles devront obligatoirement etre validees par un responsable.
Section 31
Audit et tracabilite
Les operations sensibles seront enregistrees.
Exemple :
Utilisateur : Patrick Maison : Kinshasa Action : Creation d'une vente Montant : 500 $ Date : 17/08/2026 14:32 Resultat : Succes
L'audit permettra de repondre a :

Qui a fait quoi, quand, ou et sur quelle donnee ?

Les transferts de clients, validations de commissions, modifications sensibles et operations financieres devront notamment etre tracables.
Section 32
Architecture multi-tenant
Meme si la premiere utilisation concerne une seule entreprise, le modele de donnees integrera des la V1 la notion de :
Tenant = entreprise cliente.
Chaque donnee metier importante sera rattachee au tenant.
SALES OS │ ├── TENANT A │ ├── Maisons │ ├── Agents │ ├── Clients │ └── Ventes │ ├── TENANT B │ ├── Maisons │ ├── Agents │ ├── Clients │ └── Ventes │ └── TENANT C
Une entreprise ne pourra jamais acceder aux donnees d'une autre. Cette isolation sera appliquee au niveau de la couche de donnees et verifiee par des tests specifiques.
Section 33
Architecture technique cible
Le MVP sera developpe sous forme de monolithe modulaire.
NEXT.JS / REACT │ ▼ APPLICATION CORE │ ┌────────┴────────┐ │ │ PAYLOAD CMS LOGIQUE METIER │ │ └────────┬────────┘ ▼ POSTGRESQL SOURCE DE VERITE │ REDIS Cache / Sessions / Jobs
Technologies cibles
  • Frontend : Next.js / React
  • Backend / administration : Payload CMS + logique metier
  • Base de donnees : PostgreSQL
  • Cache / jobs / temps reel futur : Redis
  • API : API versionnee
  • Deploiement : infrastructure web securisee
Le choix technologique pourra etre ajuste lors de la conception technique sans modifier les fonctionnalites validees par le present cahier des charges.
Section 34
Principe "PostgreSQL source de verite"
Toutes les donnees critiques sont conservees dans PostgreSQL.
Redis pourra etre utilise pour :
  • cache
  • sessions
  • taches
  • evenements
  • temps reel
Redis ne constituera jamais la source principale des ventes, paiements, stocks ou commissions.
Section 35
Evolution architecturale
La premiere version n'utilisera pas une architecture microservices complexe. Le systeme sera organise en modules :
AUTH TENANT USERS HOUSES CRM SALES ORDERS PAYMENTS STOCK COMMISSIONS TARGETS REPORTING AUDIT
Si la plateforme atteint une taille importante, certains modules pourront ulterieurement devenir des services independants.

  • pages principales idealement chargees en moins de 2 secondes dans des conditions normales
  • pagination et recherche pour les grandes listes
Securite
  • mots de passe haches
  • HTTPS
  • protection contre les injections
  • protection XSS
  • protection CSRF lorsque pertinente
  • controle des permissions
  • isolation tenant
  • audit
  • gestion securisee des sessions
Disponibilite
Objectif initial : 99,5 % hors maintenance planifiee, sous reserve de l'infrastructure d'hebergement.
Sauvegardes
  • sauvegardes automatiques
  • conservation de plusieurs versions
  • procedure de restauration testee
Compatibilite
Navigateurs modernes : Chrome, Edge, Firefox, Safari. Interface responsive et prioritairement adaptee aux smartphones pour les agents.
